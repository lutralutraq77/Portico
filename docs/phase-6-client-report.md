# Phase 6 development client evidence

The development Linux client now discovers the authenticated device's resource catalog and connects application pipes to an explicit resource ID/revision. It composes protected device identity, pinned private control/carrier TLS, actual inner connector authentication and the existing online workload authorization path. It is not a supported desktop client, service, package or production deployment. Phase 6 and the complete fifteen-phase objective remain in progress. No canonical case is newly promoted: seven of 91 are implemented and 84 remain planned.

See the [command contract](client-configuration.md), [process scenario](../internal/controller/client_command_linux_test.go), [machine-readable evidence](phase-6-client-evidence.json) and [delivery ledger](delivery-status.md). Final-head hosted checks are tracked in [draft PR 4](https://github.com/lutralutraq77/Portico/pull/4).

## Implementation and process evidence

Production source febe97dcb900292626058ba9b5cdf0e59294662d adds the client commands, a shared protected identity parser, strict versioned catalog responses and bounded bidirectional application copying. Source ad4fec8fea152953d0e81e54bcbceb1eefd3c469 names fields in two configuration fixtures to satisfy vet after the shared-type refactor. Source 13faa55016918dd1538620f910b2659d64a5a80e changes only the Linux client process fixture: it observes durable authority/socket counts, waits for a freshly admitted connector binding before a positive connection, and reports early process exits. Runtime code and application build hashes are identical across these three sources.

The initial regression demonstrated that a validated, consumed FIN was incorrectly replaced by a denial when an application requested EOF after carrier closure. The corrected client preserves only zero-byte EOF, without reviving byte or write authority. A consumed FIN acknowledgment also remains valid as consumption evidence after the transport closes. The stream adapter waits for request acknowledgment before returning success; each copy direction has one 32 KiB buffer and a final buffered response has a bounded drain deadline.

The guarded process scenario runs real client and connector binaries, actual mutually authenticated control/carrier/inner TLS and TEST-NET destination sockets inside a NIC-less Linux guest. It checks unsynchronized native-clock startup, an overly readable key, exact inventory, unknown resource/revision denial, forbidden destination/username/clock overrides and connector-profile substitution. Six selection/configuration denials create no authorized session or destination.

Five positive sessions exercise: (1) a 122,880-byte request whose 81,920-byte response is generated only after input EOF, with the 65,536-byte output pipe left unread until the connector has closed and reported its receipt; the application then receives the exact complete response and a successful process exit; (2) the same final-output backpressure with no resumed reader, which must terminate with failure within the five-second drain deadline plus the one-second test observation margin; (3) SIGTERM while local input is idle; (4) SIGKILL and subsequent fresh process access; (5) grant revocation with a demonstrably full output pipe, followed by denial from a new process. All five intended destinations close with authenticated connector receipts. The queued 65,536 pipe bytes after revocation were delivered before closure and cannot be recalled.

Native pipe tests confirm that the adapter owns pollable descriptions without changing the original descriptions' flags, interrupts blocked reads/writes on close, and rejects invalid directions and regular files. The positive clock fixture supplies synthetic NTP metadata only to the disposable kernel and restores it afterward; it changes neither UTC nor the host and proves no actual synchronization source.

## Retained failures and limits

The pre-fix EOF regression failed as intended on consumed_fin and retained denial on raw abandonment. Log SHA-256: BC6E959DFEF44C9A17522FC38CC956CEB2A8F2A38C21428D764E8A69BF3AB284. An earlier incomplete regression fixture panicked because its dummy connection lacked required lifecycle fields; that fixture error is not a product finding. Its source/log remain archived. The first catalog test exposed a wire-contract mismatch: the shared strict decoder requires an object, while the old HTTP catalog returned a bare slice. The handler/client now use CatalogSnapshot; malformed and obsolete shapes reject. The first full Windows attempt stopped on four unkeyed shared-type test literals; its preserved log SHA-256 is 8B0E5445B0CFD5F19A70709F21A14E2C21964B5C09339369298C614248BE6B9D.

The first full Linux attempt on febe97d failed the longer client scenario; log SHA-256 680B43FC8E5DA8518DCDEEBEFA89B3A84D904CC4A46A2B0C25A2FE5C80ED27D3. Diagnostics exposed the fixture's assumption that idle bindings remain continuously available across the deliberate five-second output stall. Actual idle expiry/rebinding is expected. The final fixture observes fresh admission and uses durable authority/destination counts for denials; it does not add production request retries or weaken authorization timeouts. One diagnostic also captured an early generic connector security-stop during concurrent heavy host verification. The connector exit path implicates its clock supervisor, but the exact rejecting clock sample was not captured. A later clock-instrumented diagnostic did not reproduce that exit. These records remain under work/reports/phase-6-client-initial/diagnostic and diagnostic-clock. The final full Linux qualification runs separately from heavy Windows checks. No time-source availability, physical suspend or Q05 acceptance is claimed.

The native file loader uses software keys and trusts the calling OS user and host administrator. Protected identity loading is not platform-keystore custody or same-user IPC isolation. Desktop/browser workflows, enrollment tooling, Arch packaging/services, Windows/Android clients, installed controller/connector deployment, independent egress isolation and the remaining acceptance matrix are still required. Final-output buffering cannot retract bytes an application has already received. The catalog envelope is a deliberate change to the private development API; no released compatibility claim exists.
