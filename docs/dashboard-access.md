# Administrator access inspection

The private dashboard now offers **Access → Inspect access**, with separate views for device grants and connector hosting. An administrator selects two exact registered certificate identities and a current resource revision. The selectors show public SHA-256 fingerprints and fetch at most 50 records per page. Historical or revoked certificate metadata remains visible; being listed does not establish a usable identity.

`POST /api/v1/admin/dashboard/access` accepts `DeviceCertificateID`, `ConnectorCertificateID`, `ResourceID`, `Revision` and an optional `PolicyRevision`. The browser always supplies its observed policy revision. The endpoint uses the existing strict administrator HTTP boundary: actual private TLS identity, exact origin, bounded JSON, no unknown or duplicate fields, and a fresh administrator authority check on every request. A policy change requires a new snapshot.

Inspection shares the authorization engine's certificate, enrollment, issuer, user/device, exact resource/grant/hosting, destination and quota reads. These run in one controller transaction without creating a session, lease or capability. Live authorization retains its sticky transaction-failure behavior. The read path distinguishes a legitimate policy denial from a storage or integrity failure; an operational failure returns no inspection result.

A positive result identifies the user/device, exact resource revision, connector, IP address, TCP port and policy expiry. The interface explains that other ports and LAN destinations need their own grants, and that opening a connection still requires fresh possession proofs, online authorization and separate application authentication. Connector availability is not asserted by a policy snapshot.

Changing a selector clears both the previous result and its status. The next combination is explicitly unchecked until another inspection succeeds. Responses must match the selected certificate principals and complete resource destination. Unexpected fields, mismatched identities/destinations, stale revisions and request failures clear the displayed state. The page stores no identity material or inventory in browser storage.

Grant and hosting inventories preserve each rule's exact stored resource revision, including old or disabled rules. Their names are joined to that revision, rather than the current resource head. Paging is bounded and revision-bound; listing a stored rule does not describe its current effectiveness.

The native tests compare a positive inspection with actual authorization, then compare seventeen denials involving live identities, pending enrollment, revocation, disabled or ambiguous rules, expiry, revision, protected destinations and quotas. Additional tests cover read-only behavior, strict HTTP input, reused-TLS administrator revocation, emergency denial, storage failure, sticky transaction failure, exact certificate choices and historical rule metadata.
