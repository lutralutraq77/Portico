# Development Linux agent catalog

The development command can retain an explicitly unlocked encrypted device identity for a bounded local session and serve fresh resource inventory:

```text
portico agent run --config /absolute/path/client.json --socket /private/path/agent.sock --prompt
portico agent catalog --socket /private/path/agent.sock
```

The run command also accepts the existing dedicated `--secrets-fd 3` input. An explicit secret source is mandatory; it loads only the version-2 encrypted client configuration and never falls back to a plaintext key. The [terminal](terminal-unlocking.md), [client configuration](client-configuration.md) and [protected local transport](local-ipc.md) contracts apply unchanged. The socket's mode-0700 parent must already exist with safe ancestors; startup does not create or repair that directory or remove a stale socket.

The generated `portico.agent.v1.Agent` gRPC service currently provides `Catalog`. Every call uses the existing client configuration to fetch a fresh authenticated controller catalog with native clock-health checks. It does not reuse cached inventory as authority, issue certificates or open a destination. The request contains only an explicit version. The bounded response carries exact resource IDs/revisions/tuples, rejects unknown fields and invalid/duplicate entries, and uses canonical UTC expiry values. The command returns versioned JSON. Errors remain fixed messages without configuration paths, private key material or backend details.

Both ends authenticate the actual effective UID through the private Unix socket before gRPC starts. No TCP listener, proxy environment, DNS lookup, browser endpoint or alternate local address is supported. The pinned gRPC local-credentials adapter identifies the already protected Unix transport; it does not replace the independent kernel UID check.

The initial limits are eight accepted connections, one concurrent RPC per connection, eight backend calls overall, 64 KiB protobuf messages, 8 KiB header lists, five-second handshake/backend deadlines and ten-second complete client calls. There is no admission queue for excess connections. A fifteen-minute unlock window uses the existing suspend-aware boot clock; missing, decreasing or expired readings permanently close it. Requests check the window before and after backend work, and a 250 ms supervisor stops the server when closure is observed. Shutdown closes transports and joins the server/handlers. The CLI process exits afterward. This does not guarantee erasure of every Go heap copy, recall already delivered bytes or qualify physical suspend scheduling.

The RPC tests exercise the actual generated protocol through protected sockets and the actual catalog command. The controller integration fixture additionally starts the real agent with the newly enrolled encrypted identity, checks exact inventory without a destination session, revokes enrollment and requires a subsequent request through the still-running agent to fail. The original encrypted state and signing count must remain unchanged. The first local enrollment integration run successfully unlocked the actual agent and returned the exact controller catalog. The existing application-transfer step then failed with EOF before any authorized session or destination socket; its failure log is retained at `work/reports/phase-6-agent-enrollment/runtime.log`, SHA-256 `a966c39358c1d4f3009d6de3fa6aa0b5e4a51fb1ae94f48f5c3749495d11c824`. Its dependent agent-denial check had not reached revocation, so the fixture now establishes that precondition independently. The process fixture also uses an explicit ten-second idle carrier pairing window, within the existing thirty-second cap, to accommodate catalog-to-carrier setup; timing diagnostics measure that interval. The generic two-second pairing and other hostile timeout cases, production open/authorization deadlines, revocation leases and KDF cost are unchanged. The process rerun is pending; the earlier failure is not relabeled as a pass.

This increment does not yet supply resource-stream RPCs, a desktop application, installed service, platform key-store provider or browser/native administrator bridge. Per-user IPC excludes other OS users; it does not isolate applications sharing the same UID or authenticate a browser origin. Those remaining boundaries stay in the [delivery ledger](delivery-status.md).
