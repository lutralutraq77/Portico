# Administrator certificate renewal

The controller has a separate administrator renewal boundary. It retains the current P-256 key, requires two enabled and separately tested factors, and consumes a fresh WebAuthn approval bound to the current administrator certificate, exact CSR, requested expiry and policy revision. Ordinary enrollment and ordinary renewal continue rejecting administrator identities.

`BeginAdminRenewal` verifies a signed CSR with empty identity claims. The requested expiry must extend the current leaf, use whole seconds and remain within the device, issuer and root expiry limits and a maximum of 24 hours. `FinishAdminRenewal` rechecks that scope and both factors while consuming the hardware approval. Approval records contain public material only. The controller permits one outstanding renewal per administrator device.

The durable states are `approved`, `issuing`, `issued`, `active` and `revoked`. The approved operation has a ten-minute completion deadline; the current leaf must also remain valid. Issuance, reconciliation, result delivery and activation reject expired or revoked authority and changes to the approved policy revision. Restoring an old factor value does not restore an earlier approval.

`IssueAdminRenewal` commits the transition to `issuing` before invoking the restricted issuer provider once. A timeout, error, restart or ambiguous result cannot automatically repeat signing. Trusted operator/provider reconciliation supplies the original public certificate through `ReconcileAdminRenewal`. The controller checks its exact authority, current key and approved dates. A different signed result cannot replace an already recorded result. Explicit local revocation can retire an uncertain attempt before a new hardware-approved request is made.

An issued candidate cannot authenticate to the normal administrator listener. `AdminRenewalTLSConfig` is a separate, activation-only transport policy; it also accepts the activated leaf for an idempotent confirmation within the original deadline. `ActivateAdminRenewal` requires an actual TLS proof with the exact issued certificate, rechecks current authority and atomically selects the new leaf, closes the initial-factor bootstrap window and removes old ceremonies. The previous leaf immediately fails new handshakes and authorization on existing TLS connections. A public certificate, old TLS connection or different private key cannot activate a renewal. Activation and its audit event commit together.

Schema 6 adds renewal state without changing earlier schema text or checksums. Upgrade preserves identities and factors, invalidates pending approvals and appends its audit event in the same transaction. Audit failure rolls back the entire upgrade. Quarantined snapshots revoke every renewal while retaining public signing evidence, and restore validation rejects a snapshot containing live renewal authority.

## Integration and qualification

The private administrator HTTPS listener provides separate challenge, confirmation and public-certificate retrieval operations. Preparation requires the policy revision the administrator reviewed and returns the exact CSR hash, current certificate hash, expiry and hardware challenge. Confirmation consumes that challenge before one issuer invocation. The ordinary listener cannot receive this signing capability, and certificate retrieval remains available without a configured provider. Replayed confirmations cannot sign again; ambiguous provider results require the existing trusted reconciliation process.

`NewAdminRenewalActivationServer` serves only the activation operation on an explicitly supplied loopback listener. It owns actual TLS connections, admits at most eight connections before TLS and at most four request bodies, rejects excess work without queuing and has a maximum five-second deadline. Its configuration contains no issuer capability. The exact host, origin, path, JSON version and bounded body are required. Cancellation drains requests and connections. Candidate authentication does not grant access to the dashboard or ordinary administrator listener.

The native command now orchestrates renewal using version-2 protected configuration and a private credential journal. The renderer selects a requested expiry and supplies actual WebAuthn proof after reviewing exact fingerprints, expiry and policy revision. Native code generates the empty-claim CSR with the existing key, retains the same request before network use, saves confirmation intent before sending proof and saves an issued candidate before attempting activation. The renderer cannot submit its own CSR, certificate, key, network target or filesystem path. The native sender can reach only the three fixed approval/result endpoints; candidate TLS permits only activation.

An uncertain confirmation is never resent. Explicit continuation retrieves the original public result; ambiguous issuer outcomes still require trusted provider reconciliation. A retained candidate survives interruption. Native code first checks its current authority on a fresh normal administrator TLS connection; if already active, it can reconcile a lost activation response even after the activation confirmation window has ended. Otherwise it uses the separately configured activation listener. Only a confirmed current identity becomes the journal's selected certificate. The completed window asks the user to close and reopen with that certificate. Startup reconciles a retained candidate before relying on its retired or expired predecessor. Review cancellation is allowed only before proof submission.

The review includes the actual stored hardware-ceremony expiry. The native client rejects an expired or nearly expired review before saving confirmation intent or sending proof, keeping it cancellable. The browser also checks that deadline before and after hardware interaction. An administrator who leaves a review open can cancel it and begin again without turning an expired review into an uncertain issuer operation. The [native renewal evidence](phase-7-administrator-native-renewal-evidence.json) records the final race and actual-window results, source hashes, preserved failures and pending Linux qualification.

Operational issuer custody, initial administrator bootstrap and independent recovery are still required. These interfaces do not establish physical key custody or owner authentication. Injected durability errors and process reopening do not establish physical power-loss resilience.
