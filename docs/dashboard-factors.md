# Administrator security-key management

The private dashboard's Security section now includes an owner-scoped key list, an exact-key test, retirement with a different key, and two-stage registration of a replacement. The list contains only the key record identifier, attested model UUID and enabled/tested state. Credential handles, public keys, attestation bodies and pending ceremonies are excluded from inventory.

Adding a key first requires approval from a currently enabled key that has already passed its separate key test. After approval, a second button lets the administrator switch to the new physical key and perform native WebAuthn registration. Registration records the new key as untested. The administrator must then select that exact key's test action. Retirement excludes the target credential from the challenge and checks the actual approving credential again at completion. The final enabled key cannot authorize its own retirement.

The initial-registration action retains the existing local ten-minute window and maximum of two historical factor records. Retiring a record does not restore this allowance. This limited primitive does not complete owner bootstrap, establish an administrator device, create an encrypted backup, or prove physical recovery readiness.

Both factor endpoints require the actual administrator TLS identity, exact private Origin, current policy revision and strict bounded JSON. New record identifiers are server-generated. The two-minute ceremony binds the stored operation and administrator device certificate to the policy revision. Completion rechecks live identity and current tested-key state before consuming the ceremony and committing the audit event. The factor completion endpoint cannot redeem policy or invitation ceremonies.

The interface checks the returned operation, target, revision, expiry, relying-party hostname and required user verification before calling the browser's native WebAuthn API. Registration also checks the administrator's user handle, cross-platform attachment and direct attestation request. Cancellation, navigation and hiding the page discard the operation and abort pending calls. Late results cannot submit an approval. A lost or invalid confirmation is reported as uncertain and is never retried automatically.

The native controller tests use real TLS, SQLite and independently generated software attestation fixtures. The browser test uses the actual embedded dashboard and native credential APIs, with CDP virtual USB keys swapped explicitly between operations. Its isolated model policy includes Chromium's publicly documented software attestation signer. An ephemeral CA with that published signer and issuer name permits normal certificate-chain verification of the virtual device's leaf; this fixture does not alter production attestation policy and must never be trusted by a deployment. The signer comes from [Chromium's virtual FIDO device source](https://chromium.googlesource.com/chromium/src/+/HEAD/device/fido/virtual_fido_device.cc), source blob `9b98eb85ccb28b02d0d6e5ed459d43f18b6f93ba`. The [virtual CTAP2 source](https://chromium.googlesource.com/chromium/src/+/HEAD/device/fido/virtual_ctap2_device.cc) defines its software model UUID.

The first six focused native race tests passed. A new regression reproduced the pre-existing ability of an untested credential to approve another operation; the controller now filters to previously tested keys at both challenge and completion. Thirty administrator/dashboard/policy tests and 87 subcases subsequently passed under the race detector in 109.36 seconds, with no failures or skips.

The complete browser recovery flow passed all 15 groups in 18.06 seconds, using Edge 152.0.4191.66 and Playwright 1.62.1. Seven native assertions and one native registration exercised the actual controller. Independent database/audit observations confirmed registration leaves the replacement untested, its separate test restores two tested keys, retirement requires the other key, and the final enabled key cannot retire itself. The test also covers altered challenge fields, stale policy, cancellation/navigation, bad UV, replay, lost confirmation, live revocation, empty browser storage and same-origin requests. Desktop and 360px dark screenshots were inspected. The existing inventory and policy browser regressions then passed all 19 and 16 groups in 11.74 and 16.23 seconds; controller vet/staticcheck with the browser tag passed. Initial registration has positive HTTP/cryptographic fixture coverage; its positive native-browser path is not separately qualified by this replacement-registration run.

Earlier failed browser runs remain recorded. The first two stopped during assertion handling while multiple virtual devices were connected; the fixture now swaps a single virtual USB device at a time. Replacement registration then exposed two fixture CA problems: the issuer's ASN.1 string encodings differed from Chromium's, and the same-subject/same-key leaf and CA were treated as a cycle. The fixture now preserves Chromium's issuer encoding and has a distinct CA SAN. The actual browser response, production trust requirements and normal X.509 verifier remain unchanged. The corrected run passed; these software identities establish no physical attestation qualification. See the [source-bound factor evidence](phase-7-factor-evidence.json).

The factor source `e3e79c5` subsequently passed all six hosted PR workflows, including 256 top-level Linux tests and 1,182 subcases with five explicit skips, plus four installed-service, 21 HTTPS and 17 SSH cases. See the [verified hosted artifacts](phase-7-factor-hosted-evidence.json). The later [user/device/connector lifecycle component](dashboard-lifecycle.md) adds record creation, rename and revocation with its own source-bound qualification.

The later [invitation administration component](dashboard-invitations.md) uses tested-key approval for ordinary device and connector enrollment creation and revocation. Complete secure bootstrap and native administrator bridge, platform key custody, encrypted backup and independent physical-console recovery, accessibility qualification and real key/private-origin tests remain required. Phases 6 and 7 and the canonical 91-case acceptance objective remain incomplete.
