# Real HTTPS application integration

`TestArchGuestApplicationHTTPS` is implemented and awaiting runtime qualification. It runs only in the dedicated NIC-less Arch guest. It exercises the actual curl executable, encrypted enrollment commands, locked agent daemon, application launcher, controller, carrier, connector and a separate production restricted-issuer process. This extends the [launcher component qualification](application-launcher.md); it does not yet establish a passing result.

The fixture creates separate application-TLS and Portico trust roots. The restricted issuer loads an encrypted PKCS8 key and accepts the authenticated registration authority's scoped issuance request. OpenSSL from the pinned Arch image creates that test-only envelope using its [documented PKCS8 command](https://docs.openssl.org/3.6/man1/openssl-pkcs8/). Ephemeral issuer custody in a disposable root process does not qualify production custody or physical hardware. The earlier fixture identity files are removed before enrollment, and the encrypted device identity supplies the agent's subsequent proof.

The first local diagnostic booted Arch and confirmed curl 8.22.0/OpenSSL 3.6.4, then failed the restricted issuer's readiness check after 89.43 seconds of test execution. That startup probe allowed only 250 milliseconds per authenticated TLS connection and ten seconds overall. The corrected fixture allows two seconds per probe and ninety seconds for separate-process startup, records the readiness duration and retains the final TLS/process error on failure. This does not change production issuance or resource deadlines. The original cause remains unproven until further evidence is collected. The failed log is retained at `work/reports/application-https-first/runtime.log`, SHA-256 `5fff545ade2438222b4e017abb1ea34cab4915268fefbb6acadc577aea66bb79`; the guest powered off and its process was joined before starting another diagnostic.

Curl uses a private Unix endpoint and the original HTTPS hostname with normal certificate verification. A protected header file provides the fixture application's separate credential; no credential appears in the command line. The destination observes the HTTP Host and TLS SNI. Cases require exact binary content with authentication, rejection before HTTP on a wrong hostname or untrusted root, HTTP authentication failure without a credential, zero new destination/authority for an ungranted resource or wrong revision, a successful control after those denials, and zero new destination after enrollment revocation. Every accepted destination must close and produce its controller receipt. Launcher endpoints must disappear, and encrypted state and single issuance must be preserved.

The second diagnostic passed authenticated issuer readiness after 62.03 seconds, completed encrypted preparation, redemption and activation, then reached the overall 240-second test timeout while collecting the agent unlock result. It did not reach a curl case. The retained `work/reports/application-https-ready/runtime.log` has SHA-256 `e0f2f7c0ac6212058bd05b082f1e4ae647ac98a5c6d2ca179326eea03c2f5655`. The process powered off and was joined. Stage timings now identify each enrollment operation and unlock. A fresh diagnostic is required; these partial observations are not an application pass.

The application fixture runs as root separately from the existing UID1000 installed-service fixture. It does not borrow that fixture's user-isolation result. Both remain in the same disposable Arch image without a NIC or host shares. The driver allows 600 seconds each for installed-service and application qualification; the guest service has a 1,300-second limit and QEMU a 1,600-second outer limit including boot. The application test spans a separate issuer startup, several production-KDF operations and eight curl cases. Its one persistent test daemon has a four-minute fixture lifetime to cover unlock and those cases; other process fixtures retain their existing limits. Production KDF, authority, stream and operation deadlines remain unchanged.

The current source also compares guest DNS/hosts files, IPv4/IPv6 routing tables and policy rules, and forwarding settings before and after the application workflow. It uses read-only observations inside the isolated guest. This ninth subcase was added after the second diagnostic binary was compiled and has no runtime result yet.

The third diagnostic completed all enrollment operations and agent unlock, then failed the positive curl cases immediately (total test 93.82 seconds). Its numbered `TempDir` child used 0777 subject to umask, while the launcher requires a 0700 immediate parent. The next fixture corrected that mode and added destination/HTTP/authentication counters. The third log is `work/reports/application-https-budget/runtime.log`, SHA-256 `bec184e528b294a4389064d94526c063de70b896f399f6407fb0db45cee10562`.

The fourth diagnostic still rejected positive cases with zero destination connections (77.46 seconds), retained at `work/reports/application-https-private/runtime.log`, SHA-256 `9867f1d6c95c1445f07b1d9c2e295faa3109b73ca69fc2f6a5aca0a9e9847e99`. Inspection identified the additional ancestor requirement: the production IPC walk rejects every group/other-writable ancestor, including sticky `/tmp`. The current fixture creates endpoints below its already-protected client configuration directory and issuer custody below a new private directory at the isolated guest root. It proves endpoint creation/cleanup and checks the unlocked agent's exact catalog before interpreting application results. Production directory checks are unchanged. Both runs reported four passing subcases, including the network snapshot, but their failed controls prevent treating the denied requests as successful end-to-end qualification. A fresh run must establish the corrected workflow.

The fifth diagnostic, with the protected ancestor paths and preconditions, failed during enrollment redemption before reaching the application cases. Issuer readiness took 51.74 seconds and encrypted preparation 41.03 seconds, compared with roughly 7 and 13–16 seconds in the earlier faster runs. Total test time was 196.84 seconds; the CLI reported preservation of the original enrollment state. The retained `work/reports/application-https-protected/runtime.log` has SHA-256 `5830b59caa6b15c3de95f781bd70ef7a770682bcaf9049344c2dda4944c8dea2`. The cause of redemption failure remains unproven. Fixture diagnostics now record issuance duration/success/context expiry and the final enrollment state without logging credentials. The corrected source is proceeding to hosted Linux qualification; production network and issuance timeouts remain unchanged.

This is a controlled HTTPS application, not Jellyfin, a browser bridge or an SSH client. Those workflows, desktop key storage, physical suspend and the remaining Phase 6 requirements remain open. No additional canonical acceptance case is claimed.
