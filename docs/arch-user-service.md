# Arch user service runtime qualification

The `Arch user service runtime` workflow builds the exact-source development package, checks its installation/removal, then creates an initramfs from the same digest-pinned Arch image. The rootfs construction runs in a fresh networkless container with read-only package/script/test inputs and one public artifact output. It does not mount host installation directories, credentials or cgroups. The guest boot uses the existing checksum-pinned Linux kernel and source-built QEMU, two virtual CPUs, 3 GiB RAM, no network adapter and no host filesystem shares. The outer runtime limit is 900 seconds, including a 600-second enrolled-identity test budget with the production KDF cost unchanged.

The fixture starts the image's real systemd as PID 1 and uses its `user@1000.service` and runtime-directory units, including PAM and the user manager's delegated cgroup hierarchy. This follows the upstream [user manager unit](https://raw.githubusercontent.com/systemd/systemd/v257/units/user@.service.in) and [resource-control documentation](https://raw.githubusercontent.com/systemd/systemd/v257/man/systemd.resource-control.xml); the recorded Arch package list and systemd version identify the actual tested implementation.

Checks observe the installed unit and binary hashes, disabled/inactive installation, explicit startup, a locked status response, denial of catalog access while locked, and another UID's failed socket access. The running process must have UID 1000, an empty effective capability set, `NoNewPrivs=1`, a seccomp filter, umask 0077, no stdin, zero core-file limit and 256-descriptor limits. Its actual cgroup files must report a 1 GiB memory maximum and 128-task maximum. Runtime directory and socket ownership/modes must be 1000:1000 with 0700 and 0600 respectively. These observations distinguish applied restrictions from unit text; a seccomp filter alone does not prove every address-family denial.

The fixture kills the main process and requires one automatic restart with a different PID and locked state. Explicit stop must remove the socket/runtime directory and process, remain stopped beyond the restart delay, and preserve the separate configuration's bytes and permissions. Restarting the user manager must leave this disabled service inactive until explicitly started again. The final package hashes must remain unchanged.

The first lifecycle stage deliberately has no provisioned identity. A second stage runs `TestSystemdGuestAgentEnrollmentAndRevocation` against actual guest-local enrollment, controller, carrier and connector fixtures. Enrollment/activation and the resource/control CLI processes execute as UID 1000; their inherited application/secret pipe inodes are also owned by that UID so the real descriptor-reopen checks apply. Only public trust files enter the user's protected configuration directory. Controller/connector private keys remain in root-owned fixture directories. Device enrollment creates the user's encrypted state, and the installed unit's unchanged command reads it on explicit unlock.

That stage requires exact inventory, binary application transfer, manual lock with destination closure, explicit re-unlock, a second transfer interrupted by a main-process crash, automatic restart locked, another explicit unlock, and a final transfer terminated by enrollment revocation. All three destination closures must have matching receipts; locked/revoked calls cannot create a new destination. Stop must remove runtime state while preserving the original encrypted key/certificate bytes, their UID/mode and the single issuance count. The test uses synthetic guest-only kernel synchronization metadata, which qualifies wiring rather than upstream time accuracy. No host clock or network settings change.

This test skips in ordinary host and minimal-guest suites, where no real user manager is present. The dedicated workflow requires its actual PASS line and rejects every skip/failure. It does not qualify production identities, desktop login/logout, physical suspend, a platform key store, real hardware or complete browser/application isolation.
