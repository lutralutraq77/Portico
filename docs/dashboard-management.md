# Administrator policy management

The private dashboard can create a TCP resource, revise its destination, add a device grant and add connector hosting permission. Resources and the two access lists provide the entry points. Selectors show at most 50 records per page, remain bound to one policy revision and retain unsent form values while paging. Permission dates are explicitly entered and displayed in UTC.

Each form submits a draft to the existing policy preview endpoint. The browser checks the returned operation, destination, identities, revision and interval against the selected draft before displaying it. Revisions show both current and proposed destinations. The server creates and retains the immutable operation, binds its digest to the administrator's actual TLS identity and policy revision, and expires it after five minutes. A preview creates no resource or permission.

The separate approval button obtains a fresh challenge and calls the browser's native WebAuthn API. The relying-party ID must equal the private hostname and user verification must be required. This implementation uses the [WebAuthn Level 3 JSON conversion methods](https://www.w3.org/TR/webauthn-3/) and rejects browsers without them. The server remains responsible for the signature, original attestation, allowed model, counter, backup eligibility, current administrator authority, two tested factor records and one-use transaction. No browser decision grants authority independently.

Cancellation and section navigation abort outstanding requests and discard the preview. Hiding or leaving the page uses the existing clearing behavior. Late credentials cannot trigger a confirmation after cancellation. The approval button cannot submit twice. A lost or invalid confirmation is reported as uncertain because the server might already have committed; the UI never retries that mutation. Refresh retrieves current configuration before another draft. Changed policy or administrator revocation requires a fresh preview.

`TestDashboardPolicyBrowser` runs the actual embedded interface against a real private TLS controller and SQLite database. A virtual USB P256 authenticator performs native browser assertions using a credential previously registered and tested by the controller. The fixture observes database counts and audit commits independently of the UI. It covers paged choices, altered previews, wrong relying party, stale policy, cancellation/navigation, invalid UV and signature, resource creation/revision, grants/hosting, replay, uncertain confirmation and administrator revocation. It also checks hostile text, keyboard focus, 360px dark reflow, 48px controls, empty browser storage and same-origin page requests.

The final management browser run passed all 16 groups in 75.66 seconds using Edge 152.0.4191.66 and Playwright 1.62.1. The existing dashboard passed all 19 regression groups in 34.94 seconds. Desktop and mobile preview screenshots were inspected. The first management run exposed a fixture error: navigating to an unchanged hash did not refresh its prior error state. The harness now explicitly reloads that document. The failed log remains separate; the corrected initial 14-group run also remains recorded. See the [source-bound evidence](phase-7-management-evidence.json).

The focused server boundary regression passed ten top-level tests and 60 subcases under the native race detector in 80.788 seconds. It covers authenticated private assets, hostile HTTP requests, live revocation, exact policy previews, atomic one-use approvals and backup-factor recovery. Controller vet/staticcheck with the browser build tag and JavaScript syntax checks passed.

This is a Phase 7 component. [Security-key administration and backup-authorized replacement](dashboard-factors.md) now have separate implementation and component evidence. User/device/connector lifecycle screens, complete recovery, secure bootstrap, the native administrator bridge, full accessibility and physical key/origin qualification remain unfinished. The TLS identity and authenticator are software fixtures, so these results establish neither production key custody nor physical recovery readiness. Phases 6 and 7 and the canonical 91-case acceptance objective remain incomplete.
