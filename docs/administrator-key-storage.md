# Linux administrator key storage

The `internal/adminkey` component implements the encrypted-file baseline in the platform plan. It creates a new P-256 administrator device key locally and publishes encrypted state before returning a signer. Opening an existing file validates Linux ownership, permissions, file type, link count, size and durability before decrypting it. The containing directory must be private (0700); new key files use 0600. Existing files are never overwritten, and rejected opens do not repair caller-owned permissions.

The encrypted record has a distinct administrator purpose and binds the deployment, principal, administrator profile, issuer ID and both pinned authority certificate hashes. Approved public trust is supplied independently. Stored metadata cannot establish another deployment, issuer, role or principal. Ordinary enrollment retains its separate format and ordinary-only API.

Encryption uses the existing pinned age dependency and scrypt work factor 18. Input sizes and passphrase encoding/length are bounded; one expensive operation is admitted at a time without a queue. Decryption caps the accepted work factor and consumes authenticated EOF before exposing plaintext. Truncation, tampering, appended data and wrong passwords are rejected. The key must use canonical P-256 PKCS#8 encoding; duplicate or unexpected record fields are rejected.

The returned handle implements `crypto.Signer`. Its public-key view is a separate decoded value, and private key bytes are not exported. Closing the handle prevents further signatures through previously returned TLS identities and waits for a signature already holding its mutex. The handle can create a proof-of-possession CSR without identity, extension or validity claims. A TLS identity requires a certificate from the supplied administrator trust for the bound principal and the same public key. Live registration, revocation, session lifetime and hardware approval remain transport/controller decisions.

This is software custody protected by encryption and Linux filesystem controls. The OS user and administrator remain trusted, and Go/age internal allocations prevent a forensic-erasure claim. A failed create after publication must be reconciled by opening the original file; generating a replacement key is not a retry strategy. No invitation bearer secret, certificate activation flag or browser session is stored here.

The [administrator command](administrator-command.md) now loads an existing key and certificate through protected configuration and owns their native-session lifetime. A supported installer, issuance/renewal ceremony and recovery integration remain unfinished. This does not complete administrator bootstrap or physical-key qualification.
