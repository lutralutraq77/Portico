# Private enrollment invitation administration

Administrators can create invitations for existing ordinary devices or connectors and revoke an existing enrollment from the Enrollments screen. The create form selects an enabled identity and an already-bound issuer of the same profile, with an invitation expiry within one hour and an explicit certificate expiry within current authority. The review shows the exact identity, owner where applicable, issuer, times and server-generated enrollment identifier. No invitation exists and no secret is generated during review.

The private challenge and confirmation endpoints require the actual administrator TLS identity and exact Origin. Both operations require two previously tested registered keys to be available, and a fresh assertion from a currently tested key. The stored operation, certificate identity and current policy revision are bound to the WebAuthn ceremony. Completion consumes the proof and commits the enrollment mutation with its audit events in one transaction. Invitation, factor and resource-policy confirmation endpoints reject one another's ceremonies.

Only a successfully committed creation response contains the random invitation secret. The database stores its hash; inventory, issuer metadata, challenges and audit records contain no token or token hash. There is no later secret-retrieval endpoint. The browser shows the secret once in a readonly field, supports immediate hiding, removes it on navigation and schedules removal after at most one minute. It does not copy to the clipboard, put the token in a URL, or use persistent browser storage. A lost response is uncertain and is never retried automatically; the reviewed enrollment identifier can be used to revoke the lost invitation before creating another.

Revocation acts on the enrollment, including any certificate issued through it. It preserves the record, denies further token reuse and certificate authentication, removes dependent controller session authority and queues cancellation. It cannot revoke the current administrator device's enrollment or a connector serving an enabled management resource. These guards are checked before staging and again at completion. Destination socket closure remains subject to separate runtime qualification.

The first focused native race run passed four tests and 22 subcases in 80.72 seconds. It used actual TLS keys and in-process profile-restricted signing fixtures to create, redeem, activate and revoke both device and connector enrollments. Other checks cover malformed drafts, the administrator-profile boundary, Origin, expiry, stale authority, audit rollback, live revocation, two-key readiness and cross-endpoint replay. An earlier test build failed because it named a nonexistent audit helper; the corrected fixture uses the existing audit verifier. The [source-bound evidence](phase-7-invitation-evidence.json) records the final broader regression and browser checks.

The final broader native race regression passed 46 tests and 145 subcases in 399.32 seconds, without failures or skips, including the new bound issuer metadata and pagination checks. Controller vet and staticcheck passed with and without the browser build tag. The existing inventory, policy, factor and lifecycle browser regressions passed 19, 16, 15 and 14 groups in 37.60, 44.34, 80.45 and 68.22 seconds. Together with the invitation flow, all 75 browser groups passed on the combined source.

The invitation browser run passed 11 groups in 26.20 seconds, using Edge 152.0.4191.66 and Playwright 1.62.1. It exercises native WebAuthn against the actual embedded dashboard and controller, one-time secret display, metadata redaction, changed previews, cancellation, invalid user verification, stale policy, lost responses and administrator revocation. The actual generated device token was redeemed through the controller, activated with its TLS key, used for session authorization and then revoked through the browser. Screenshots capture only the review before any secret exists; desktop and 360px dark layouts were inspected. Immediate hiding and navigation were tested; the full sixty-second display timeout was not separately timed.

The preceding lifecycle source `40cd1da` passed the hosted Linux guest but failed repository quality because its independent-administrator fixture was unused in the standard build. The invitation tests now use that fixture in the standard build, without suppressing static analysis. The Arch run passed installed-service checks but failed two authenticated HTTPS repetitions before reaching SSH. These are separate outcomes, recorded in the [lifecycle hosted evidence](phase-7-lifecycle-hosted-evidence.json); no fix to the intermittent application failure is claimed.

This component uses virtual security keys and an ephemeral TLS proxy for isolated tests. Complete owner bootstrap, the native administrator bridge, platform key custody, administrator credential renewal, encrypted backup and independent physical-console recovery remain open. It does not establish physical-key or deployment readiness, finish Phases 6 and 7, or change the seven implemented and 84 planned canonical acceptance cases.
