# Fresh bindings for encrypted agent transfer tests

The encrypted daemon fixture now observes a newly admitted connector binding before starting each already-unlocked agent transfer. The fixture's relay permits ten seconds for pairing, but its connector client cancels an unpaired open after three seconds. A `Waiting == 1` snapshot alone can therefore describe an attempt that is about to expire. Password processing during explicit re-unlock makes that snapshot unsuitable as the positive transfer precondition.

The fixture waits at most eight seconds before starting the subprocess, matching the existing configured-client fixture's approach. The controller, connector and agent still use their original open, authorization, lease and stream deadlines. Failed application data is never retried. Direct encrypted clients still establish their initial binding at the first controller request, after their production password KDF.

Both hosted predecessor sources `c703ddc` and dashboard `b1be43a` failed the fresh transfer after daemon lock/re-unlock before a second destination connection or authorization. Their preceding live transfer and lock checks passed. A separate compiler-instrumented guest passed all seventeen daemon subcases in 233.10 seconds, so it did not establish the original rejection's cause. The timing issue above is visible in the fixture and carrier-client code; this correction is not proof that every historical failure shared that cause.

The uninstrumented NIC-less Linux guest passed all seventeen daemon subcases in 211.23 seconds, with no failures or skips. It exercised exact bytes through manual lock and re-unlock, fresh authorization, enrollment revocation, closure receipts, socket cleanup and retention of the original encrypted identity. Linux controller vet and staticcheck also passed. The [source and artifact record](phase-6-daemon-binding-evidence.json) binds this result to the changed fixture.
