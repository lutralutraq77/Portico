# Initial administrator key browser qualification

The initial-registration browser fixture starts with a locally provisioned administrator TLS identity and zero registered factors. Two empty virtual USB authenticators, connected one at a time, use the browser's actual WebAuthn registration API against the private dashboard. Neither credential is imported. Normal attestation verification uses the isolated Chromium software model described in [security-key management](dashboard-factors.md); production trust and registration rules are unchanged.

The corrected run passed all 12 groups in 48.76 seconds, with two native registrations and three native assertions. Independent database and audit-event counts confirm each registration leaves its key untested, each separate exact-key test marks only that credential tested, and the second key can retire the first. An untested first key cannot approve replacement registration. A third initial registration is denied; retiring the primary does not reopen the allowance. Replayed confirmations and live administrator revocation are rejected.

Changed relying-party, administrator handle, attestation, attachment and verification requirements stop before native creation. Cancellation produces no registration or confirmation. The flow leaves no cookies or browser storage, makes only same-origin page requests and has no script errors. Desktop and 360px dark review screenshots were inspected, including heading focus and minimum button height. The first run stopped on a fixture navigation error: returning to the same URL retained the error view. Explicit reload now matches the existing browser harness behavior; that failed run remains recorded.

The existing replacement-key browser regression passed all 15 groups in 48.95 seconds using the extended shared harness. Controller vet/staticcheck with the browser build tag and JavaScript syntax validation passed. The [evidence record](phase-7-initial-key-evidence.json) identifies source files, browser results and regression checks.

This qualifies the initial key-registration primitive. The administrator device and its TLS identity still come from fixture setup. Complete owner bootstrap and finalization, secure native administrator bridge, platform custody, credential renewal, encrypted backup and independent physical recovery remain required. Virtual USB keys do not prove physical hardware backing or independent custody. Phases 6 and 7 remain incomplete.
